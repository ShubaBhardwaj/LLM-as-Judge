# Design Decisions & Trade-offs

This document outlines the core technical design decisions, trade-offs, and risk mitigations implemented in the **LLM-as-Judge Evaluation Pipeline**.

---

## 1. Which Judging Mode Did You Pick and Why?

**Selected Mode:** **Pairwise A-vs-B Comparison**

### Rationale:
1. **Relative Judgments Are More Reliable:** Large Language Models demonstrate superior consistency when performing relative comparisons between two candidate outputs side-by-side, compared to assigning absolute pointwise numerical scores (which suffer heavily from score clustering and calibration drift).
2. **Independence From Reference Answers:** Pointwise reference-based grading requires comprehensive gold-standard solutions for every prompt, which fails to scale for open-ended or creative tasks. Pairwise evaluation evaluates candidate outputs against the prompt constraints and explicit rubric standards directly.
3. **Clear Model Comparison:** For comparing candidate generator architectures (Groq/Llama vs Gemini), pairwise judging yields unambiguous win/loss/tie decisions per question without requiring arbitrary score thresholding.
4. **Anonymized Symmetrical Evaluation:** Candidates are presented as Option A and Option B, stripping provider names to eliminate model-name bias.

---

## 2. How Do You Parse Structured Verdicts and Recover from Malformed JSON?

**Selected Strategy:** **Multi-Stage Resilient Fallback Parser (`parse_judge_response`)**

### Implementation Pipeline:
1. **Stage 1 — Standard JSON Parsing & Pydantic Validation:** Strips markdown block formatting (` ```json ... ``` `) and parses JSON string directly into `RawJudgeOutput` Pydantic model.
2. **Stage 2 — Key Normalization:** Handles common LLM key formatting variations (e.g. `Option A`, `option_a`, `A` -> normalized to `option_a`).
3. **Stage 3 — Regex Substring Extraction:** If GPT includes conversational preambles or malformed outer JSON, regex extracts inner `{...}` blocks and attempts re-parsing.
4. **Stage 4 — Key-Value Regex Fallback:** Extracts `winner`, `scores`, and `reason` values using individual key pattern matching.
5. **Stage 5 — Controlled Default Object:** If all recovery fails, returns a default `RawJudgeOutput` object (`winner="tie"`, scores=3.0, reason="Controlled fallback: Failed to parse response").
6. **Auditable Error Logging:** All parsing outcomes (`success`, `fallback_regex_json`, `fallback_regex_kv`, `fallback_controlled_default`) are recorded in `logs/judge_calls.jsonl`.

**Result:** The FastAPI application and batch evaluation suite **never crash** due to raw JSON parsing errors.

---

## 3. Why GPT-4o-Mini as Judge Instead of Groq or Gemini?

**Selected Strategy:** **Model Family Separation**

### Rationale:
1. **Mitigating Self-Enhancement Bias:** LLMs exhibit a documented bias toward outputs generated by their own model family or training distribution. Using Groq (Llama-3.3-70b) or Gemini to judge their own outputs introduces self-favoritism.
2. **Provider Separation:** The generators are **Groq** (`llama-3.3-70b-versatile`) and **Gemini** (`gemini-2.5-flash`). Using **OpenAI** (`gpt-4o-mini`) as the judge ensures that neither generator belongs to the judge's model family.
3. **Cost & Latency Balance:** `gpt-4o-mini` offers near-GPT-4 level reasoning quality for structured JSON evaluation at lower latency and cost compared to full `gpt-4o`.

*Note:* Model family separation reduces self-enhancement risk but does not entirely eliminate general style preferences inherent to OpenAI models.

---

## 4. Which Bias Worried You Most?

**Selected Bias:** **Position Bias (Order Preference)**

### Rationale & Mitigation:
- **The Problem:** LLM judges frequently favor whichever candidate answer is presented first (**Option A**) regardless of quality.
- **The Mitigation (Double-Pass Swap):** For every evaluation, the pipeline performs two passes using the **exact same pre-generated answers** (without regenerating text):
  - **Pass 1:** Option A = Groq, Option B = Gemini -> record `winner_ab`
  - **Pass 2:** Option A = Gemini, Option B = Groq -> record `winner_ba`
- **Position Flip Detection:** If the winner flips (`winner_ab != winner_ba`), `position_flip = true` and position bias is flagged.
- **Measurement:** The suite reports `position_flip_count` and `position_flip_rate` in `results/report.json` and `results/bias_results.json`.

---

## 5. Would You Let This Judge Gate a Release?

**Decision:** **No — Not without Automated Guardrails and Human-in-the-Loop Oversight.**

### Guardrails Required Before Production Release Gating:
1. **Flip Rate Threshold:** Release gating should automatically abort if the position flip rate on the evaluation suite exceeds **10%**.
2. **Adversarial Probe Pass Rate:** The judge model must maintain a **>85% pass rate** on adversarial probes (verbosity and sycophancy probes).
3. **Score Clustering Inspection:** If standard deviation across criterion scores drops below **0.3**, the judge suffers from score saturation and cannot distinguish quality differences.
4. **Human Spot Audits:** High-stakes or near-tie decisions (overall score difference < 0.2) must trigger human spot-checking before gating production deployments.
